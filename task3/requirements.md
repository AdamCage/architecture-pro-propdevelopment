# Task3 — Требования к внешним интеграциям «Умный дом»

## 0. Предлагаемое изменение ландшафта (кратко)

Проблема кейса: **внешние API партнёров используются без единых политик безопасности и контроля данных**, из-за чего возможны:
- утечки/подмена данных между разными управляющими компаниями/ЖК;
- ошибки авторизации (в т.ч. показ «чужих данных» в личном кабинете);
- слабая управляемость интеграций и аудит.

Предложение: внедрить **единый сервис-интегратор** `smart-home-adapter-app` (adapter/gateway pattern) как *единственную* точку взаимодействия с платформой партнёра «Умный дом».
- Мобильное приложение **никогда** не обращается к партнёру напрямую.
- `tenant-core-app` обращается к адаптеру по внутреннему каналу (mTLS), а адаптер уже общается с партнёром.
- Все входящие события от партнёра принимаются только адаптером, проходят проверку подписи/контракта и далее транслируются во внутренние системы.

---

## 1. Требования к безопасности (must-have)

### 1.1. Сегментация и сеть
1. Взаимодействие с партнёром — **только по TLS**; желательно **mTLS** (двусторонняя аутентификация сертификатами).
2. Входящие callback/webhook запросы от партнёра принимаются **только на выделенный endpoint** в `smart-home-adapter-app`.
3. IP-allowlist/ASN-allowlist для партнёра (где возможно) + ограничения по географии/сетям.
4. Внутренний вызов `tenant-core-app → smart-home-adapter-app` проходит внутри периметра (service mesh / внутренний LB) и защищён mTLS.
5. Обязательны rate-limit, throttling, circuit-breaker для внешних вызовов (защита от деградации и злоупотреблений).

### 1.2. Контроль данных и минимизация
1. **Минимизация данных**: в запросах к партнёру не передавать лишние ПДн.
2. **Биометрия** (шаблоны/вектора лица) и «сырые» изображения/видео **не должны храниться** в PropDevelopment (если бизнес не требует и не оформлены юридические основания). Хранить только:
   - reference ID / external ID (идентификатор в системе партнёра),
   - признаки согласия (consent),
   - журналы операций.
3. Для распознавания номера авто — в PropDevelopment хранить только **номер/маскированный номер** и связи «собственник/квартира ↔ разрешённые ТС» (если требуется), без «сырого» медиаконтента.
4. События умного дома (открытие двери/шлагбаума) должны журналироваться как **аудит** (кто/когда/что/где), но без избыточных ПДн.

### 1.3. Шифрование и управление секретами
1. Шифрование трафика: TLS 1.2+ (лучше 1.3), запрещены слабые шифры.
2. Шифрование данных на хранении для БД `smart-home-db` (at-rest encryption, TDE/диск).
3. Ключи/секреты (client secret, private keys, сертификаты) — только в secrets management (Vault/KMS/Secret Manager), **не в коде** и не в репозитории.
4. Ротация секретов и сертификатов по регламенту, поддержка немедленной ротации при инциденте.

### 1.4. Аутентификация и авторизация
1. Любая команда «открыть/разрешить/отозвать доступ» должна проверяться на уровне `tenant-core-app`:
   - пользователь аутентифицирован,
   - есть право на конкретный ЖК/подъезд/устройство (сквозная модель «tenant/building boundary»),
   - соблюдён принцип минимальных привилегий.
2. Внешний партнёр **не должен** получать возможность выполнять операции в PropDevelopment по умолчанию. Входящие webhook’и — только события/уведомления по контракту.
3. Запрет «сквозного доверия»: даже если партнёр передал `owner_id`, PropDevelopment повторно проверяет соответствие (не «верим на слово»).

### 1.5. Валидация контрактов и защита API
1. На `smart-home-adapter-app` обязателен **строгий контрактный контроль**:
   - schema validation (OpenAPI/JSON schema),
   - отклонение неизвестных/лишних полей (при необходимости),
   - нормализация данных.
2. Idempotency для команд (idempotency-key) + защита от replay (timestamp/nonce).
3. Таймауты и ретраи с экспоненциальной паузой; отдельный DLQ/parking для «ядовитых» событий (poison messages).

### 1.6. Журналирование, мониторинг, аудит
1. Журналировать:
   - команды (кто инициировал, что, где, результат),
   - входящие события от партнёра,
   - ошибки подписи/аутентификации/авторизации,
   - аномалии (повтор запросов, всплеск ошибок).
2. Логи защищены от изменения (WORM/append-only), ретеншн согласован с ИБ.
3. Корреляция: `correlationId/traceId` сквозь `tenant-core → adapter → partner`.
4. Экспорт событий безопасности в SIEM (если есть) либо подготовка формата для последующего подключения.

## 2. Протоколы аутентификации и авторизации (рекомендация)

### 2.1. Пользователь → PropDevelopment
- **OIDC/OAuth2** через `auth-service-1 (Keycloak)` для мобильного приложения.
- Access token короткоживущий + refresh token по политике.

### 2.2. PropDevelopment → Партнёр
- **OAuth2 Client Credentials** (service-to-service) + **mTLS**.
- Скоупы минимальные: отдельные client credentials per environment (DEV/QAS/PROD) и по возможности per partner/UK.
- Вызовы только от `smart-home-adapter-app`.

### 2.3. Партнёр → PropDevelopment (webhook)
- mTLS + **подпись запроса**:
  - вариант A: JWT (JWS) с ключом партнёра (kid + rotation),
  - вариант B: HMAC signature в заголовках + timestamp/nonce.
- Обязательная защита от replay: окно времени + одноразовые nonce.

## 3. Организация взаимодействия (как это работает)

### 3.1. Команды (синхронный путь)
1. Собственник инициирует действие в мобильном приложении (например, «Открыть дверь»).
2. `tenant_showcase → tenant-core-app`: REST/WS, токен Keycloak.
3. `tenant-core-app` проверяет права (user ↔ объект ↔ устройство) и пишет аудит.
4. `tenant-core-app → smart-home-adapter-app`: REST (mTLS).
5. `smart-home-adapter-app → partner`: внешний API (mTLS + OAuth2).
6. Ответ возвращается по цепочке. При недоступности партнёра — деградация (сообщение, повтор, очередь).

### 3.2. События (асинхронный путь)
1. Партнёр отправляет событие: распознавание лица/номера, попытка доступа, открытие.
2. `partner → smart-home-adapter-app`: webhook (mTLS + подпись).
3. Адаптер:
   - проверяет подпись/время/схему,
   - отбрасывает лишние данные,
   - пишет аудит/лог,
   - публикует событие в PropDevelopment (внутренний REST или очередь/топик).
4. `tenant-core-app` формирует уведомление и отправляет push через FCM/APNS.

### 3.3. Данные и хранение
- `smart-home-db` хранит только:
  - привязки устройств и объектов,
  - правила/разрешения доступа,
  - события и результаты команд (без биометрии/медиа).
- Передача данных в DWH — только после минимизации/маскирования, по утверждённым правилам Data Governance.

---

## 4. Нефункциональные требования к интеграции

1. SLA внешнего партнёра фиксируется договором (доступность, задержка, окна обслуживания).
2. Observability: метрики latency/error-rate по endpoint’ам партнёра.
3. Версионирование контрактов API (v1/v2) и договорённость по backward compatibility.
4. Контроль изменений: тестовый стенд партнёра, контрактные тесты, «canary» для новой версии.
5. Регулярная оценка рисков: аудит партнёра, пентест интеграции, пересмотр моделей угроз.
